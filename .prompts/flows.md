# 開発手順

## 1. 設計書の作成（対話形式）

実装を開始する前に、以下の設計書を順番に作成します。各設計書作成時は、不明点や確認事項をユーザーに質問しながら進めてください。

### 1.1 要件定義書 (docs/requirements.md)

以下の内容を含めて作成:

- 背景と目的
- 機能要件（ユーザーストーリー形式）
- 非機能要件（パフォーマンス、セキュリティ等）
- 制約事項
- 受け入れ条件

質問例:

- 「この機能の主な使用者は誰ですか？」
- 「どのような状況でこの機能が使われますか？」
- 「パフォーマンスやセキュリティに関する要求はありますか？」

### 1.2 技術設計書 (docs/design.md)

1.1 要件定義書 (docs/requirements.md)を元に、以下の内容を含めて作成:

- アーキテクチャの概要
- 使用する技術スタック
- データフロー図
- API 設計（該当する場合）
- エラーハンドリング方針

質問例:

- 「既存のアーキテクチャで考慮すべき点はありますか？」
- 「使用したい特定の技術やライブラリはありますか？」
- 「API の認証方式はどうしますか？」

### 1.3 実装計画 (docs/tasks.md)

1.2 技術設計書 (docs/design.md)を元に、以下の内容を含めて作成:

- タスクの分解（優先順位付き）
- テストケースの定義（TDD 用）
- リスクと対策

質問例:

- 「優先的に実装すべき機能はどれですか？」
- 「テストの網羅性はどの程度を目指しますか？」
- 「想定されるリスクはありますか？」

## 2. 設計レビューと承認

全ての設計書が完成したら、ユーザーに最終確認を求めます:

```
設計書の作成が完了しました。以下の内容で実装を開始してよろしいですか？

- 要件定義書: docs/requirements.md
- 設計書: docs/design.md
- 実装計画: docs/tasks.md

確認事項:
1. 要件に不足はありませんか？
2. 技術的な方針に問題はありませんか？
3. 実装順序は適切ですか？
```

## 3. TDD による実装

承認を得たら、以下の順序で実装を進めます:

1. **テストケースの作成**: docs/tasks.md に定義したテストケースを実装
2. **テストの実行**: 失敗することを確認
3. **最小限の実装**: テストが通る最小限のコードを実装
4. **リファクタリング**: コードの品質を向上
5. **次のテストケースへ**: 1-4 を繰り返す

## 4. 進捗報告

タスクを順次実行し、進捗を`docs/tasks.md`に更新する

コミットするときに以下を満たす

- 意味のある単位である
- 実装をした場合はテストをパスしている
